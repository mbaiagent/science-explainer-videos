一个反直觉的账

把一个 80 亿参数的开源模型（Llama 3.1 8B）部署到 GPU 上，模型权重用 BF16 存放，大约占 15 GiB 显存。现在让它读一份 12.8 万 token 的长文档，再回答一个问题。你可能以为显存主要花在模型身上，但算一下就会发现：仅仅为了「记住」这份文档，推理过程中要额外保存一份叫 KV Cache 的数据，大约 16 GiB，比模型本身还大。

如果同时有 16 个用户、每人 3.2 万 token 的上下文，KV Cache 就是 64 GiB。一张 80 GB 的 GPU，放下权重之后，剩下的空间能服务多少人，基本由 KV Cache 决定。

这就是本文标题里「内存条」的意思：

  • token 是模型读写文字的最小单位，也是计费单位；
  • 上下文窗口是模型一次能「看到」的 token 上限，相当于内存条的容量；
  • KV Cache 是这些 token 在推理时真正占用的显存，是内存条上实际存的东西。

这三件事连在一起，解释了很多日常现象：为什么中文和英文的账单不一样，为什么输出比输入贵好几倍，为什么「支持 100 万 token」的模型在长文档里还是会漏掉信息，为什么提示词缓存能让首字延迟明显降低、价格降到原来的一个零头。

本文假设你大致了解 Transformer 里的 Q、K、V 和自注意力。不熟悉的话，可以先看本系列《Transformer 详解》，那篇在结尾提到了 KV Cache，本文把它展开讲透。

Token：模型眼里的文字

模型不认识字，只认识编号

大模型的输入输出都是数字。文字在进入模型之前，要先经过分词器（tokenizer）切成一个个小片段，每个片段在词表里有一个编号，这个片段就叫 token。模型每一步做的事情，就是根据前面所有 token 的编号，预测下一个 token 的编号（见本系列《什么是 LLM》）。

切分的粒度怎么选？有三种思路：

切分方式 例子 优点 问题
按字符 / 字节 l o w e s t 词表很小，任何文本都能表示 序列太长，模型要多算很多步，也更难学到词义
按完整单词 lowest 序列短 词表巨大；没见过的词（新词、拼写错误、人名）无法表示
子词（subword） low + est 常见词是一个 token，罕见词拆成几块 需要一个算法决定怎么拆

现在的大模型几乎都用子词方案，最常用的算法是 BPE（Byte Pair Encoding，字节对编码）。

BPE：反复合并最常见的一对

BPE 最早是一种数据压缩算法，2016 年被 Sennrich 等人用到神经机器翻译里，用来处理罕见词。它分训练和编码两步。

训练（在大量语料上做一次，得到词表和合并规则）：

  1. 把每个词拆成最小单位（字符或字节），这些单位就是初始词表；
  2. 统计语料里所有相邻两个 token 出现的次数；
  3. 把出现次数最多的那一对合并成一个新 token，加入词表，并记下这条合并规则；
  4. 重复第 2、3 步，直到词表达到目标大小（比如 10 万）。

编码（每次处理新文本时做）：把文本拆成最小单位，然后按训练时的顺序依次重放合并规则，能合并的就合并。

结果是：the、ing、模型 这种高频片段会变成一个 token；罕见的词会被拆成几块；完全没见过的字符串，最差也能退回到最小单位，永远不会出现「不认识」的情况。

字节级 BPE：从 256 个字节出发

如果最小单位是「字符」，问题就来了：Unicode 有十几万个字符，还有表情符号和各种罕见文字，初始词表就很大，而且总会碰到训练时没见过的字符。

GPT-2 采用了字节级 BPE：先把文本转成 UTF-8 字节序列，最小单位是字节，初始词表只有 256 个。任何文本，不管什么语言、有没有乱码，都能表示成字节序列，再在字节上做合并。今天的主流分词器（包括 GPT 系列使用的 tiktoken、Llama 3 的分词器）基本都是这个思路。

字节级带来一个对中文很重要的细节：一个汉字在 UTF-8 里占 3 个字节。如果分词器的训练语料里中文多，常用汉字和词语会被合并成 1 个 token；如果中文少，一个汉字可能要用 2～3 个 token 表示。后面的代码会直接演示这个现象。

实际的分词器还会先用正则表达式把文本粗切成「词」（比如字母、数字、标点、空格分开），合并只在这些片段内部进行，避免出现「单词尾巴 + 标点」这种没意义的 token。

词表多大

分词器 词表大小 出处
GPT-2 50,257 GPT-2 论文
Llama 3 128,000（其中 10 万来自 tiktoken，另加 2.8 万个改善非英语的 token） 《The Llama 3 Herd of Models》

词表越大，同样的文本切出来的 token 越少（每个 token 平均包含更多字符），但输出层和词向量矩阵也越大。Llama 3 论文给出的数据是：换成新分词器后，英文样本的压缩率从每个 token 3.17 个字符提高到 3.94 个字符。

中文、英文、代码各多少 token

这是最常被问到、也最容易说错的问题。答案取决于具体的分词器，同一段文字，换个模型 token 数就不一样。下面是几家官方给出的说法：

来源 官方说法
OpenAI 帮助文档 英文：1 个 token 约等于 4 个字符，约等于 3/4 个单词；100 个 token 约 75 个单词。并注明这些只是估算
DeepSeek API 文档 1 个英文字符约 0.3 个 token，1 个中文字符约 0.6 个 token；实际以返回的 usage 为准
Llama 3 论文 英文样本上平均每个 token 3.94 个字符
Anthropic 定价文档 Claude 4.7 及之后的模型使用新分词器，同样的文本大约多出 30% 的 token（具体因内容而异）

由此可以得到一个粗略的估算口径：

  • 英文：1,000 个单词大约 1,300 个 token；
  • 中文：差别最大。中文语料充足的分词器（如 DeepSeek 的说法），1,000 个汉字约 600 个 token；中文覆盖少的分词器，可能接近甚至超过 1 字 1 token。做预算时宁可按 1 字 1 token 高估；
  • 代码：没有查到权威的统一换算。代码里大量的缩进空格、括号、长标识符都会占 token，通常可以按英文的量级估算，但偏差可能不小。

准确的数字只有一个来源：用该模型的分词器去数。 OpenAI 提供开源的 tiktoken 库，Anthropic 提供 token 计数接口，几乎所有 API 的响应里都有 usage 字段。本文的运行环境无法下载 tiktoken 的词表文件，所以没有贴真实分词器的计数结果，这一点请以你自己的实测为准。

为什么按 token 计费

因为模型的计算量和 token 数直接相关：

  • 每个输入 token 都要经过所有层的计算；
  • 每生成一个输出 token，都要把整个模型完整地跑一遍（下一节细讲）；
  • 每个 token 在推理过程中都要占一份 KV Cache 显存。

token 是最贴近成本的计量单位。

为什么输出比输入贵

以 Anthropic 官方定价为例（美元 / 百万 token，核实时间 2026 年 10 月）：

模型 输入 输出 命中缓存的输入
Claude Opus 5.5 4 20 0.20
Claude Sonnet 5.5 2 10 0.10
Claude Haiku 5.5（提示 ≤ 10 万 token） 0.10 0.50 0.01

输出单价是输入的 5 倍，其他厂商的比例不尽相同，但输出贵于输入是普遍现象。定价当然有商业考虑，但根本原因在于成本结构不同：输入可以一次并行算完，输出只能一个一个生成。这个差别要从推理的两个阶段说起。

表里最后一列「命中缓存的输入」只有普通输入的 1/20，原因在本文最后的「提示词缓存」一节。

上下文窗口：一次能放多少

上下文窗口（context window）是模型单次请求能处理的 token 总数上限。注意它通常是输入和输出共用的：输入 90 万 token，窗口 100 万，那么输出最多只剩 10 万（还要受单独的最大输出长度限制）。超出窗口的内容，模型根本看不到。

窗口大小的变化很快：早期的 GPT-3 只有 2,048 个 token，Llama 2 是 4,096，Llama 3.1 是 128K；Anthropic 的定价文档写明，Claude 4.6 及之后的模型（Haiku 5.5 除外）以标准价格提供完整的 100 万 token 窗口。

窗口大小由什么决定

1. 训练时见过多长的序列。 模型只在训练长度以内学会了怎么用位置信息。超出训练长度，效果通常会急剧下降。所以长窗口要专门训练：按 Llama 3 论文的描述，它先在 8K 的窗口上做常规预训练，再分六个阶段逐步把窗口扩展到 128K，这一过程用了约 8,000 亿 token；每个阶段都要等模型恢复短文本上的表现、并能在当前长度上通过「大海捞针」测试之后才进入下一阶段。

2. 位置编码能不能「外推」。 自注意力本身不知道 token 的先后顺序，需要位置编码。现在主流的 RoPE（旋转位置编码）把位置转换成向量的旋转角度（见《Transformer 详解》）。直接把位置编号用到训练时没见过的大数，模型会遇到从没见过的角度组合，表现变差。几种常见的扩展办法：

方法 思路（点到为止）
位置插值（Position Interpolation，Chen et al. 2023） 不让位置号超出训练范围，而是把位置号「压缩」回原来的范围内；论文用不到 1,000 步微调，把 LLaMA 的窗口扩展到 32,768
调大 RoPE 的基数 θ 让旋转变慢，长距离的位置也能区分开；Llama 3 把 θ 设为 500,000
NTK-aware、YaRN 等 对不同频率的分量区别处理，在扩展长度的同时尽量保留短距离的精度

这些方法都需要配合一定量的长文本继续训练，不是改个参数就能免费获得长窗口。

3. 算力和显存。 注意力的计算量随长度平方增长，KV Cache 随长度线性增长。窗口能做多大，也受推理成本约束。Haiku 5.5 在提示超过 10 万 token 后单价变为原来的 5 倍，就是长上下文成本的一个直接体现。

能放下，不等于能用好

窗口大小是「能装下多少」，不是「能用好多少」。本系列《上下文工程》里介绍过 中间遗忘（Lost in the Middle）：Liu et al. 的研究发现，相关信息放在长输入的开头或结尾时，模型答得最好；放在中间时效果明显下降，呈 U 形曲线，某些设置下甚至不如完全不给文档。Chroma 等机构的后续测试也表明，无关内容越多，模型越容易出错（他们称为「上下文腐烂」），虽然具体的 U 形规律并不总能复现。

还要注意，「大海捞针」这类测试只要求模型找到一句明显不同的话，比真实任务简单得多。能在 100 万 token 里找到一根针，不代表能在 100 万 token 里做好需要综合多处信息的推理。

工程上的结论是：窗口是上限，不是目标。能检索的就检索，能压缩的就压缩，关键信息放在开头或结尾。

推理的两个阶段：预填充与解码

模型处理一次请求，分成两个性质完全不同的阶段。

预填充（prefill）：一次算完整个提示词

提示词的所有 token 在请求到达时都已经知道了，所以可以一次性并行地送进模型：几千个 token 组成一个大矩阵，每一层都是大矩阵乘法。GPU 最擅长这种计算，计算单元能被充分利用，瓶颈在算力（compute-bound）。

预填充结束时，模型得到两样东西：

  • 第一个输出 token；
  • 提示词里每个 token 在每一层的 K 和 V，存进 KV Cache，供后面使用。

解码（decode）：一次只生成一个 token

之后的输出只能逐个生成：第 2 个 token 依赖第 1 个，第 3 个依赖前两个。每一步只有一个新 token 进入模型，但为了这一个 token，GPU 要把全部模型权重从显存读一遍，还要读出所有历史 token 的 K、V。

读了几十 GB 数据，只做了一个 token 的计算，计算单元大部分时间在等数据，瓶颈在显存带宽（memory-bound）。

可以粗算一下单个请求的速度上限：Llama 3.1 8B 的权重约 16 GB，H100 SXM 的显存带宽官方规格约 3.35 TB/s。每生成一个 token 至少要读一遍权重，所以单请求解码速度的理论上限约为 3,350 ÷ 16 ≈ 200 token/秒，实际还要更低。这也是推理服务一定要做批处理（batching）的原因：把很多请求的「当前 token」拼在一起，读一次权重，同时算几十个请求，权重读取的代价就被摊薄了。

而批处理能拼多少个请求，又受限于每个请求的 KV Cache 要占多少显存。KV Cache 越大，同时能服务的人越少，单位 token 的成本就越高。这就是长上下文和长输出贵的原因之一。

TTFT 与 TPOT

衡量推理延迟的两个常用指标正好对应这两个阶段：

指标 含义 主要取决于
TTFT（Time To First Token） 从发出请求到收到第一个 token 的时间 预填充：提示词长度、排队时间、有没有命中缓存
TPOT（Time Per Output Token），也常说 ITL（token 间延迟） 之后每个 token 之间的平均间隔 解码：模型大小、显存带宽、批大小、上下文长度

一次请求的总耗时约等于 TTFT + TPOT × (输出 token 数 − 1)。

聊天场景用流式输出，用户最在意 TTFT；Agent 往往要等完整输出才能执行下一步，总耗时更重要，而输出 token 数通常是大头。所以让模型少说废话，往往比缩短输入更能提速（详见本系列《Agent 的成本与延迟》）。

回到计费问题：输入 token 在预填充中被并行处理；输出 token 每个都要单独占一次「读全部权重」的解码步，还在生成期间一直占着 KV Cache。同样一个 token，作为输出的成本远高于作为输入，这是输出更贵的根本原因。

由于两个阶段特性不同，现代推理框架还会做专门的调度：比如把很长的预填充切成小块，和其他请求的解码步穿插执行（分块预填充，chunked prefill），避免一个长提示词卡住所有人的生成；也有系统把预填充和解码放到不同的 GPU 上分别处理（常称为 PD 分离）。

KV Cache：把算过的 K、V 存下来

不缓存会怎样

回顾自注意力：每个 token 的向量 x 分别乘以三个矩阵，得到 q、k、v。第 t 个位置的输出，是用它的 qt 去和第 1 到 t 个位置的 k 做点积，softmax 之后对 v 加权求和。

假设已经生成了 1,000 个 token，要生成第 1,001 个。最朴素的做法是把这 1,001 个 token 整个送进模型，每一层重新算出所有位置的 q、k、v 和注意力，最后只取最后一个位置的输出。下一步再把 1,002 个 token 全部重算一遍……

问题在于：前 1,000 个位置的 k、v，上一步已经算过了，而且完全没变。

为什么历史的 K、V 不会变

关键在于因果掩码：每个位置只能看到自己和前面的 token，看不到后面的。所以第 i 个位置在每一层的计算结果，只取决于前 i 个 token。后面再生成多少新 token，都不会影响它。

这样一来，第 i 个位置在每一层的 ki、vi 一旦算出，就永远不变，可以直接存起来。每一步只需要：

  1. 对新 token 算出它在每一层的 q、k、v；
  2. 把新的 k、v 追加到这一层的缓存末尾；
  3. 用新 token 的 q 和缓存里全部的 K、V 做注意力。

这就是 KV Cache。每一层、每个注意力头都有自己的一份。

为什么不缓存 Q

因为历史的 Q 以后再也用不到了。

qi 的作用是「第 i 个位置去查询别人」，用来算第 i 个位置的输出。这个输出在生成第 i+1 个 token 时已经用过了，由于因果掩码，它以后不会再改变，也不会再被需要。而新 token 要和所有历史位置的 k、v 打交道：它的 q 要和每个 k 做点积，然后对每个 v 加权求和。

一句话：Q 是「提问者」，每次只有新 token 在提问；K、V 是「被查询的资料」，所有历史 token 都要随时被查到。所以要缓存的是 K 和 V。

代价：用显存换计算

不缓存时，生成第 n 个 token 要处理 n 个位置，生成 N 个 token 的总计算量随 N 的平方甚至更快地增长；有了缓存，每步投影部分的计算量是常数，只有注意力部分随长度线性增长。后面的 NumPy 实验会实际数一下乘法次数。

代价是显存：每个 token 在每一层都要存一份 k 和 v。

显存公式

KV Cache 字节数 = 2 × 层数 × KV 头数 × 头维度 × 序列长度 × batch × 每个数的字节数

  • 2：K 和 V 各一份；
  • 层数：每一层都有自己的注意力；
  • KV 头数 × 头维度：一个 token 在一层里的 k（或 v）向量长度。多头注意力（MHA）中 KV 头数等于注意力头数；用了 GQA 的模型，KV 头数更少（下一节讲）；
  • 序列长度 × batch：一共缓存了多少个 token；
  • 每个数的字节数：BF16/FP16 是 2，FP8 是 1。

代入 Llama 3.1 8B 的官方配置（《The Llama 3 Herd of Models》Table 3：32 层，32 个注意力头，8 个 KV 头，隐藏维度 4,096，所以头维度 = 4,096 ÷ 32 = 128）：

每个 token = 2 × 32 层 × 8 个 KV 头 × 128 维 × 2 字节 = 131,072 字节 = 128 KiB
128K 个 token（131,072）= 128 KiB × 131,072 = 16 GiB
模型（BF16） 每 token 4K 32K 128K
Llama 2 7B（MHA，32 个 KV 头） 512 KiB 2 GiB 16 GiB 64 GiB（仅为对比：Llama 2 实际窗口只有 4K）
Llama 3.1 8B（GQA，8 个 KV 头） 128 KiB 0.5 GiB 4 GiB 16 GiB
Llama 3.1 70B（GQA，80 层，8 个 KV 头） 320 KiB 1.25 GiB 10 GiB 40 GiB

再乘以并发数：8B 模型、每个请求 32K 上下文、同时 16 个请求，KV Cache 就是 64 GiB。这就是开头那个「反直觉的账」。

给 KV Cache 减肥

从公式看，能减小的项有：KV 头数、每个数的字节数、需要缓存的序列长度，以及显存管理中的浪费。对应四类技术。

1. 少存几个头：MQA 与 GQA

多头注意力里，每个头都有自己的 Q、K、V。但研究发现，K、V 不一定需要那么多份：

  • MQA（Multi-Query Attention，Shazeer 2019）：所有 Q 头共用同一组 K、V。KV Cache 缩小为原来的 1/头数，解码大幅加速，但模型质量可能下降；
  • GQA（Grouped-Query Attention，Ainslie et al. 2023）：折中方案，把 Q 头分组，每组共用一组 K、V。论文显示 GQA 的质量接近多头注意力，速度接近 MQA。

GQA 现在几乎是开源模型的标配。Llama 3 的 8B、70B、405B 都是 8 个 KV 头，8B 有 32 个 Q 头，相当于每 4 个 Q 头共用一组 K、V，KV Cache 是同规模多头注意力的 1/4。上一节表格里，Llama 2 7B（多头注意力）每 token 512 KiB，Llama 3.1 8B 只有 128 KiB，差别就来自这里。

更激进的做法是改变 K、V 的表示方式。DeepSeek-V2 提出的 MLA（Multi-head Latent Attention）把 K、V 压缩成一个低维的潜在向量再缓存，论文称与 DeepSeek 67B 相比，KV Cache 减少了 93.3%。

2. 每个数少用几个字节：量化 KV

模型权重可以量化，KV Cache 也可以。把 KV 从 BF16（2 字节）存成 FP8（1 字节），显存直接减半，同样的显存能放下更多 token 或更多并发请求。vLLM 支持 FP8 的 KV Cache（参数 kv_cache_dtype，可选 fp8、fp8_e4m3、fp8_e5m2 等），文档建议用校准数据来获得最好的精度，并提醒滑动窗口注意力等层对 KV 量化更敏感，可以跳过这些层。

学术界还有 4 比特甚至 2 比特的 KV 量化研究。比特数越低，省得越多，对精度的影响也越需要评测确认。

3. 只存最近的：滑动窗口注意力

如果每个 token 只看最近 W 个 token，那么只需要缓存最近 W 个位置的 K、V。Mistral 7B 就用了滑动窗口注意力，窗口 W = 4,096：

  • 缓存是一个固定大小为 W 的环形缓冲区，第 i 个位置的 K、V 存在 i mod W 的位置，旧的被新的覆盖；
  • 论文称在 3.2 万 token 的序列上，这让缓存的显存减少了 8 倍，而不影响模型质量；
  • 虽然每层只看 4,096 个 token，但信息可以逐层往后传，32 层叠起来，理论上的注意力范围约 13.1 万个 token。

纯滑动窗口会损失对远处细节的精确回忆，所以一些模型把滑动窗口层和全局注意力层交替使用，在显存和长距离能力之间折中。

4. 减少浪费：PagedAttention

早期的推理系统为每个请求预留一整段连续的显存，大小按「最大可能长度」算。问题是事先不知道模型会输出多少：预留多了浪费，不同请求长短不一又会产生碎片。vLLM 团队发现，当时已有的系统因为碎片和过度预留，浪费了 60%～80% 的 KV Cache 显存。

PagedAttention（Kwon et al.，SOSP 2023，即 vLLM 的核心技术）借鉴了操作系统的虚拟内存：

  • 把每个请求的 KV Cache 切成固定大小的块（block），每块存若干个 token 的 K、V；
  • 块在物理显存中不需要连续，用一张块表记录「第几个逻辑块在哪个物理块」；
  • 生成到新块时才分配，浪费最多是最后一块没填满的部分。

用他们的话说：块相当于页，token 相当于字节，请求相当于进程。vLLM 的博客称，这样的显存浪费不到 4%；论文报告在相同延迟下，吞吐量是 FasterTransformer、Orca 等系统的 2～4 倍。

分块还带来一个额外的好处：共享。并行采样多个回答、束搜索时，多个序列的公共前缀只需要存一份，博客称这能减少最多 55% 的显存。这个思路再往前走一步，就是提示词缓存。

四类技术对比

技术 减小公式里的哪一项 代价
MQA / GQA / MLA KV 头数（或每 token 的 KV 维度） 要在训练时就采用（或额外训练转换），可能影响质量
KV 量化 每个数的字节数 可能损失精度，需要评测
滑动窗口 需要缓存的序列长度 对远距离信息的精确回忆变弱
PagedAttention 显存管理中的浪费 实现复杂，注意力计算要能处理不连续的块

它们可以叠加使用：一个 GQA 模型，用 vLLM 部署，打开 FP8 KV Cache，再开启前缀缓存，是很常见的配置。

提示词缓存：复用的就是前缀的 KV

为什么只能复用前缀

前面说过，第 i 个位置的 K、V 只取决于前 i 个 token。反过来说，只要两个请求的前 i 个 token 完全相同，它们前 i 个位置的 K、V 就完全相同，可以直接复用，不必重新预填充。

但只要中间有一个 token 不同，从这个位置开始，后面所有位置的 K、V 都会不同：第一层的 k、v 虽然只和当前 token 和位置有关，但从第二层起，每个位置的输入都已经混入了前面所有 token 的信息。所以缓存只能从开头逐个比对，遇到第一个不同的 token 就停止。这就是提示词缓存总是强调「前缀」的原因。

推理框架里的前缀缓存

vLLM 的自动前缀缓存（Automatic Prefix Caching）建立在分块的基础上：

  • 给每个填满的 KV 块算一个哈希值，输入包括父块的哈希和本块的 token（以及 LoRA 等额外信息）。因为包含父块哈希，一个块的身份由它之前的全部内容决定；
  • 新请求到来时，按哈希查找已经算过的块，命中的直接复用，引用计数加一；
  • 请求结束后，引用计数为 0 的块并不立即清除，而是进入空闲队列，显存不够时按 LRU 淘汰。

SGLang 的 RadixAttention 用基数树（radix tree）组织不同请求的前缀，思路类似。

API 厂商的提示词缓存

各家 API 把这件事做成了「提示词缓存」（prompt caching）产品：命中缓存的部分跳过预填充，TTFT 更低、价格更便宜。以 Anthropic 当前的定价为例，Claude Opus 5.5 普通输入 4 美元 / 百万 token，缓存命中只要 0.20 美元（1/20）；写入缓存（5 分钟有效期）是 5 美元，比普通输入贵 25%。

为什么命中这么便宜：预填充是输入阶段最主要的计算，命中缓存就省掉了这部分计算；为什么写入反而更贵：服务端要额外把这些 K、V 保存一段时间，占用显存或其他存储。所以缓存只在会被反复使用的长前缀上划算。

具体的规则（是否自动、最短长度、有效期、怎么查看命中）各家不同，本系列《上下文工程》里有一张对比表。工程上的要点只有一条：稳定不变的内容放前面，变化的内容放后面，只追加、不修改。在系统提示开头放一个时间戳，就等于每次请求都从头重算。

动手实验

实验一：手写一个字节级 BPE

只用标准库，在一段很小的中英文混合语料上训练 30 次合并，观察合并过程和 token 数的变化，再用学到的规则去编码新文本：

from collections import Counter

def train_bpe(text, num_merges):
    """字节级 BPE：从 UTF-8 字节出发，反复合并出现次数最多的相邻一对。"""
    # 先按空格粗切成「词」，合并不跨词（真实分词器用正则做这一步）
    words = Counter(text.split(" "))
    # 每个词表示成字节序列；初始词表就是 256 个字节，任何文本都能表示
    corpus = {tuple(bytes([b]) for b in w.encode("utf-8")): n for w, n in words.items()}
    merges = []
    for step in range(1, num_merges + 1):
        pairs = Counter()
        for seq, n in corpus.items():
            for a, b in zip(seq, seq[1:]):
                pairs[(a, b)] += n
        if not pairs:
            break
        (a, b), freq = pairs.most_common(1)[0]
        merges.append((a, b))
        new_corpus = {}
        for seq, n in corpus.items():
            out, i = [], 0
            while i < len(seq):
                if i + 1 < len(seq) and seq[i] == a and seq[i + 1] == b:
                    out.append(a + b); i += 2
                else:
                    out.append(seq[i]); i += 1
            new_corpus[tuple(out)] = n
        corpus = new_corpus
        total = sum(len(s) * n for s, n in corpus.items())
        if step <= 8 or step % 10 == 0:
            print(f"第{step:>2}次: {show(a)} + {show(b)} → {show(a + b)}（出现 {freq} 次），语料共 {total} 个 token")
    return merges

def encode(text, merges):
    """编码：按训练时的合并顺序，依次在新文本上重放合并规则。"""
    tokens = []
    for w in text.split(" "):
        seq = [bytes([b]) for b in w.encode("utf-8")]
        for a, b in merges:
            out, i = [], 0
            while i < len(seq):
                if i + 1 < len(seq) and seq[i] == a and seq[i + 1] == b:
                    out.append(a + b); i += 2
                else:
                    out.append(seq[i]); i += 1
            seq = out
        tokens.extend(seq)
    return tokens

def show(bs):
    try:
        return "'" + bs.decode("utf-8") + "'"
    except UnicodeDecodeError:                 # 半个汉字，无法单独解码
        return "<" + bs.hex(" ") + ">"

corpus = ("low lower lowest newer newest wider widest " * 3 +
          "模型 大模型 语言模型 模型推理 " * 3)
print("初始 token 数（= 字节数，不含空格）:", len(corpus.replace(" ", "").encode("utf-8")))
merges = train_bpe(corpus, 30)

for text in ["lowest", "slowest", "大模型推理", "缓存"]:
    toks = encode(text, merges)
    print(f"{text}: {len(text.encode('utf-8'))} 字节 → {len(toks)} 个 token:", " ".join(show(t) for t in toks))

几个值得注意的地方：

  • token 数一路下降：语料从 225 个字节 token，经过 30 次合并降到 51 个。词表变大，序列变短，这就是 BPE 的本质：用词表大小换序列长度；
  • 「模型」花了 6 次合并才成为一个 token：每个汉字 3 个字节，两个字共 6 个字节。中间还出现了 <e6 a8 a1 e5> 这种「一个半汉字」的 token，它单独解码不出任何字符。真实的字节级分词器里也存在这种跨字符边界的 token；
  • 没见过的词也能编码：slowest 不在语料里，被拆成 s + lowest；
  • 语料决定了中文的「价格」：「推理」只在语料里出现了 3 次，30 次合并还没轮到它，所以被拆成 6 个字节；「缓存」从未出现，6 个字节就是 6 个 token，相当于 1 个汉字 3 个 token。中文语料少的分词器对中文更「贵」，就是这个原因。

实验二：迷你自回归解码，对比「每步重算」与「KV Cache」

用 NumPy 写一个单层注意力的玩具模型（随机权重，不会生成有意义的文字，但计算过程和真实模型一致）。对同一个 200 token 的提示词，分别用两种方式贪心生成，统计矩阵乘法里的乘法次数，并检查两种方式生成的 token 是否完全一致：

import time
import numpy as np

rng = np.random.default_rng(0)
V, D = 50, 64                      # 词表大小、向量维度
E  = rng.normal(size=(V, D))       # 词向量（随机权重，只为演示计算过程）
Wq, Wk, Wv, Wo = (rng.normal(size=(D, D)) / np.sqrt(D) for _ in range(4))
Wout = rng.normal(size=(D, V))     # 输出层：向量 → 每个词的分数
P = rng.normal(size=(4096, D)) * 0.1   # 简化的位置向量

mults = 0                          # 统计乘法次数
def matmul(a, b):
    global mults
    mults += a.shape[0] * a.shape[1] * b.shape[1]
    return a @ b

def softmax(x):
    x = np.exp(x - x.max(axis=-1, keepdims=True))
    return x / x.sum(axis=-1, keepdims=True)

def attend(q, K, Vv):
    """q: (n,D) 只能看见自己和之前的位置（因果掩码）。"""
    n, total = q.shape[0], K.shape[0]
    s = matmul(q, K.T) / np.sqrt(D)
    mask = np.triu(np.ones((n, total), dtype=bool), k=total - n + 1)
    s[mask] = -np.inf
    return matmul(softmax(s), Vv)

def generate_naive(prompt, steps):
    """不缓存：每生成一个 token，都把全部历史重新算一遍。"""
    ids = list(prompt)
    for _ in range(steps):
        x = E[ids] + P[:len(ids)]
        Q, K, Vv = matmul(x, Wq), matmul(x, Wk), matmul(x, Wv)
        h = matmul(attend(Q, K, Vv), Wo) + x
        logits = matmul(h[-1:], Wout)             # 只需要最后一个位置的输出
        ids.append(int(logits.argmax()))
    return ids

def generate_cached(prompt, steps):
    """KV Cache：预填充一次算出所有 K、V；之后每步只算新 token。"""
    ids = list(prompt)
    x = E[ids] + P[:len(ids)]                      # 预填充：整段 prompt 一次并行算完
    Kc, Vc = matmul(x, Wk), matmul(x, Wv)
    h = matmul(attend(matmul(x, Wq), Kc, Vc), Wo) + x
    ids.append(int(matmul(h[-1:], Wout).argmax()))
    for _ in range(steps - 1):                     # 解码：每步只有 1 个新 token
        x = E[ids[-1:]] + P[len(ids) - 1:len(ids)]
        q, k, v = matmul(x, Wq), matmul(x, Wk), matmul(x, Wv)
        Kc, Vc = np.vstack([Kc, k]), np.vstack([Vc, v])   # 追加到缓存
        h = matmul(attend(q, Kc, Vc), Wo) + x
        ids.append(int(matmul(h, Wout).argmax()))
    return ids

prompt = rng.integers(0, V, size=200).tolist()
for steps in (50, 200, 800):
    mults = 0; t = time.perf_counter()
    a = generate_naive(prompt, steps)
    m1, t1 = mults, time.perf_counter() - t
    mults = 0; t = time.perf_counter()
    b = generate_cached(prompt, steps)
    m2, t2 = mults, time.perf_counter() - t
    print(f"生成 {steps:>3} 个 token：输出一致={a == b}  "
          f"乘法 {m1/1e6:8.1f}M vs {m2/1e6:6.1f}M（{m1/m2:5.1f} 倍）  "
          f"耗时 {t1*1000:7.1f}ms vs {t2*1000:5.1f}ms")
print("生成的前 12 个 token id:", b[len(prompt):len(prompt) + 12])

输出（乘法次数是确定的；耗时每次运行可能不同）：

生成  50 个 token：输出一致=True  乘法    508.0M vs   10.8M（ 47.2 倍）  耗时    47.5ms vs   4.0ms
生成 200 个 token：输出一致=True  乘法   3363.7M vs   19.9M（168.7 倍）  耗时   303.8ms vs  12.4ms
生成 800 个 token：输出一致=True  乘法  50124.2M vs   85.4M（586.9 倍）  耗时  6167.8ms vs  78.7ms
生成的前 12 个 token id: [6, 32, 40, 24, 10, 21, 3, 4, 49, 34, 19, 39]

结论很直观：

  • 结果完全一致：KV Cache 是纯粹的计算优化，不改变模型的输出（真实系统里可能因为浮点运算顺序不同产生极小的数值差异，但不是近似算法）；
  • 差距随长度急剧扩大：生成 50 个 token 时相差 47 倍，800 个时相差约 587 倍。不缓存时，第 n 步要对全部 n 个位置重做投影和注意力；有缓存时，投影只算 1 个位置，只有注意力随长度线性增长；
  • 预填充那一步，两种方式的计算量一样。KV Cache 省的是解码阶段的重复计算。

真实的推理框架（如 Hugging Face Transformers 的 past_key_values、vLLM）做的是同一件事，只是每一层、每个头都有一份缓存。

实验三：KV Cache 显存计算器

把公式写成函数，代入真实模型的公开配置：

def kv_cache_bytes(layers, kv_heads, head_dim, seq_len, batch=1, bytes_per_elem=2):
    """KV Cache 显存 = 2(K 和 V) × 层数 × KV 头数 × 头维度 × 序列长度 × batch × 每个数的字节数"""
    return 2 * layers * kv_heads * head_dim * seq_len * batch * bytes_per_elem

GiB = 1024 ** 3
# 配置来自官方公开资料：《The Llama 3 Herd of Models》Table 3；Llama 2 7B 为多头注意力（KV 头数 = 头数）
models = {
    "Llama 2 7B (MHA)":  dict(layers=32, kv_heads=32, head_dim=128),
    "Llama 3.1 8B (GQA)":  dict(layers=32, kv_heads=8,  head_dim=128),
    "Llama 3.1 70B (GQA)": dict(layers=80, kv_heads=8,  head_dim=128),
}

print("每个 token 的 KV Cache（BF16，2 字节）:")
for name, cfg in models.items():
    print(f"  {name:<19} {kv_cache_bytes(**cfg, seq_len=1) / 1024:6.0f} KiB")

print("\n不同上下文长度（batch=1，BF16）:")
lengths = [4_096, 32_768, 131_072]
print(f"  {'上下文长度':<14}" + "".join(f"{n:>13,}" for n in lengths))
for name, cfg in models.items():
    row = "".join(f"{kv_cache_bytes(**cfg, seq_len=n) / GiB:>9.1f} GiB" for n in lengths)
    print(f"  {name:<19}{row}")

cfg = models["Llama 3.1 8B (GQA)"]
print("\nLlama 3.1 8B，32K 上下文，同时服务 16 个请求:")
for label, nbytes in [("BF16", 2), ("FP8 ", 1)]:
    print(f"  {label}: {kv_cache_bytes(**cfg, seq_len=32_768, batch=16, bytes_per_elem=nbytes) / GiB:.0f} GiB")
print(f"  （对比：8B 模型权重本身，BF16 约 {8e9 * 2 / GiB:.0f} GiB）")

工程实践与常见坑

估算与计费

  • 用目标模型的分词器计数：不同模型的 token 数可能差很多。Anthropic 的文档就提醒，换用新分词器的模型后，同样的提示词 token 数可能多出约 30%，即使单价不变，账单也会变化；
  • 以 usage 为准：账单和限流都按接口返回的 token 数计算，自己估算只用于预算；
  • 中文预算宁可高估：不确定时按 1 字 1 token 估算；
  • 别忘了输出也占窗口：max_tokens 设得太大，可能导致「输入 + 最大输出」超过窗口而被拒绝；
  • 控制输出长度：输出单价更高、生成更慢。要求结构化、简短的输出，往往是最直接的降本提速手段（见《Prompt 工程与结构化输出》）。

长上下文

  • 窗口是上限，不是目标：先检索、筛选、压缩，再放进上下文（见《RAG 是什么》《上下文工程》）；
  • 关键信息放开头或结尾，问题和指令放在长文档之后，减少中间遗忘的影响；
  • 注意长提示的阶梯价格：一些模型超过某个长度后单价会变化，长上下文请求要单独核算成本；

用好提示词缓存

  • 稳定的内容放前面：工具定义 → 系统提示 → 长文档 → 对话历史 → 本轮问题；
  • 前缀要逐字节稳定：时间戳、随机 ID、不稳定的 JSON 键顺序都会让缓存失效；
  • 观察命中率：响应里有缓存命中的 token 数字段，命中率是 Agent 成本和延迟的关键指标；
  • 低频请求别强行缓存：写入比普通输入贵，缓存过期前没人复用就是白花钱。

自己部署模型

  • 显存预算 = 权重 + KV Cache + 激活和开销。先用公式算清楚目标上下文长度和并发数下 KV Cache 要多少；
  • 不要把最大长度设得远超实际需要：推理框架通常按最大长度规划 KV 空间（参考写法：vLLM 的 --max-model-len、--gpu-memory-utilization 参数），设得过大会挤占并发；
  • 优先选 GQA 模型，按需开启 FP8 KV Cache 和前缀缓存，开启前后都要用评测集验证质量（见《评估（Evals）》）；

一段参考写法（vLLM 离线推理，参数名以你使用的版本文档为准，未在本文环境中运行）：

from vllm import LLM, SamplingParams

llm = LLM(
    model="meta-llama/Llama-3.1-8B-Instruct",
    max_model_len=32768,          # 按实际需要设置，不要盲目拉满
    kv_cache_dtype="fp8",         # KV Cache 用 FP8 存储，显存减半
    enable_prefix_caching=True,   # 相同前缀复用 KV 块
)
outputs = llm.generate(["……"], SamplingParams(max_tokens=256))

高频面试题速答

Q：什么是 token？中文一个字是一个 token 吗？ token 是分词器切出的文本片段，模型按 token 读写和计费。中文不一定 1 字 1 token：取决于分词器，常用词可能 1 个 token，中文覆盖少的分词器里一个汉字可能是 2～3 个 token。准确值要用对应模型的分词器计数。

Q：BPE 的训练过程是怎样的？ 从最小单位（字节）出发，反复统计相邻 token 对的频率，把最高频的一对合并成新 token 并记录规则，直到词表达到目标大小。编码时按规则顺序重放合并。

Q：为什么输出 token 比输入 token 贵？ 输入在预填充阶段一次并行处理，GPU 利用率高；输出只能逐个生成，每个 token 都要读一遍全部权重和 KV Cache，属于访存密集，而且在生成期间一直占用显存、限制并发。

Q：预填充和解码有什么区别？ 预填充并行处理整个提示词，算力密集，决定 TTFT；解码每步生成一个 token，访存密集，决定 TPOT。总延迟约等于 TTFT + TPOT × 输出 token 数。

Q：KV Cache 为什么只缓存 K 和 V，不缓存 Q？ 因果掩码保证历史位置的 K、V 不会随新 token 改变，可以复用；而每一步只有新 token 需要用 Q 去查询，历史的 Q 以后不会再被用到。

Q：KV Cache 占多少显存？ 2 × 层数 × KV 头数 × 头维度 × 序列长度 × batch × 字节数。Llama 3.1 8B 在 BF16 下每 token 128 KiB，128K 上下文约 16 GiB。

Q：GQA 是什么，为什么能省显存？ 把 Q 头分组，每组共用一组 K、V，KV 头数变少，KV Cache 按比例缩小。Llama 3 8B 有 32 个 Q 头、8 个 KV 头，KV Cache 是多头注意力的 1/4。

Q：PagedAttention 解决了什么问题？ 连续预分配导致的碎片和过度预留。它把 KV Cache 分成固定大小的块，按需分配、不要求连续，用块表映射，还能在请求间共享相同的块。

Q：为什么提示词缓存要求前缀相同？ 第 i 个位置的 K、V 依赖前 i 个 token 的全部内容。只有从开头开始完全相同的部分，K、V 才相同、才能复用；中间改一个 token，后面全部失效。

Q：模型支持 100 万 token，是不是就可以把所有资料都塞进去？ 不是。窗口只是上限：越长越贵、越慢，而且研究表明长输入中间的信息更容易被忽略。应该先检索和压缩，把关键信息放在开头或结尾。

总结

  • token 是模型读写的最小单位，由 BPE 等子词算法得到；字节级 BPE 从 256 个字节出发反复合并，任何文本都能表示。不同语言、不同分词器的 token 数差别很大，以计数接口和 usage 为准；
  • 按 token 计费，因为计算量和显存都与 token 数直接相关；输出更贵，因为解码只能逐个进行、访存密集，还长期占用显存；
  • 上下文窗口由训练长度、位置编码的外推能力和推理成本共同决定；能放下不等于能用好，要提防中间遗忘；
  • 推理分预填充（并行、算力密集、决定 TTFT）和解码（逐个、访存密集、决定 TPOT）两个阶段；
  • KV Cache 缓存历史 token 的 K、V，避免解码时重复计算；显存 = 2 × 层数 × KV 头数 × 头维度 × 长度 × batch × 字节数，长上下文时可以超过模型权重本身；
  • 减小 KV Cache 的四类技术：GQA/MQA/MLA（少存头）、KV 量化（少用字节）、滑动窗口（少存长度）、PagedAttention（少浪费）；
  • 提示词缓存复用的就是相同前缀的 KV：省掉预填充，所以更快、更便宜；稳定内容放前面、只追加不修改，才能命中。
